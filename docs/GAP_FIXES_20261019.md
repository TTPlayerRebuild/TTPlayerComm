# ttpcomm 差异修正与验证（2026-10-19）

## 1. 本次结果

按 [修正前差异审计](GAP_AUDIT_20261019.md) 的顺序，完成 F1—F7，并明确 ReplayGain 非有限输入和旧 CPU 的处理。验证中另确认并修正 CoolSB 的退出线程竞态。修正涉及 **ttpcomm DLL、共享 SDK 和重建播放器调用端**，需要一起更新。

原版 67 个有效导出、序号 12／78 的释放别名及接口版本 `0x00050700` 保持兼容；500—503 四个扩展入口、标准运行 ABI 1、归档流 ABI 2／卷组 ABI 3 的布局不变。没有把原版私有 ID3 接口改成另一套标准接口，也没有重新引入 DLL 回退。

根目录原版 `ttpcomm.dll` 未修改。测试源码、原版参考文件、样本和日志仅在本地 `rebuild/tests`，没有加入发行包或 Actions。本次没有推送或创建远程发行。

## 2. 修正清单

| 编号 | 修正 | 保留的行为与边界 |
| --- | --- | --- |
| F1 | EQ 提交先为全部处理声道预留输出队列，再消费输入、推进滤波状态 | 分配失败可以重试同一批数据；不丢失 overlap，不让声道进度错开；正常块处理、reset 和 EOF 规则保持原样 |
| F2 | SSRC 上／下采样构造使用临时分配所有者，全部成功后才交给实例 | 构造任意分配点失败都会清理；成功对象仍由原析构路径释放，不修改重采样公式 |

| F5 | 标签、封面和 ReplayGain 保存时，处理未知帧的 tag-alter 状态位 | 修改标签后丢弃标记失效的帧；音频未变，因此保留仅标记 file-alter 的帧；修改的字段重新生成，未修改的保留帧维持原字节 |
| F6 | RAR 已知成员缓存先在引擎锁之外复核实际卷组身份，再决定是否重新发现 | 同时验证路径、文件 ID、大小、mtime、ChangeTime、当前换卷映射、密码及限制；不能仅按首卷名称命中 |

另修正两个相关边界：标准标签解码后保留实际 payload 在 owned storage 中的偏移；归档卷组能力查询失败时清空函数表，避免调用未验证的入口。

### 2.1 EQ 与 SSRC 的失败恢复

原版依据沿用审计中已固定的二进制证据：EQ 提交 `60007520`／块处理 `60006FE0`，SSRC 初始化 `60005590`／上采样 `6000D230`／下采样 `6000E460`。

EQ 之前在 `queue.insert` 失败时留下 `used=511`，下一次提交会越界。本次预留所有声道容量后才开始改变逻辑状态，先前声道即使已经扩容，也没有消费数据。容量采用几何增长，避免连续提交、尚未读取时每批重新分配。

SSRC 原构造中保存的是裸指针；构造抛出时，派生类析构不会替它们清理。现在由局部所有者跟踪每次分配，在构造末尾提交所有权。原有成功清理、队列读取、Finish／reset 和滤波状态没有替换。

### 2.2 标准标签与原版私有接口

这次修正针对重建播放器使用的标准服务。原版私有 v2.4 长度等行为继续由旧接口适配，不能用标准帧规则整体替换旧接口。

标准扩展头采用独立 CRC 校验：v2.3 在整标签反同步之后验证帧区，不含 padding；v2.4 验证存储帧及 padding，不含扩展头和 footer。SDK 内使用小型 CRC 表，不要求只用帧扫描的调用方额外链接 zlib。规则依据：[ID3v2.3](https://id3.org/id3v2.3.0)、[ID3v2.4](https://id3.org/id3v2.4.0-structure)。

保存安全策略保持保守：修正读取不等于允许任意编码帧重写；原先因反同步、压缩或其它编码标志而拒绝改写的输入，并未自动开放写入。损坏 CRC 的文件保存失败时保持文件不变。

### 2.3 RAR 缓存、超时和密码

缓存候选只在短暂缓存锁内取得快照。随后在缓存锁和 UnRAR 引擎锁之外，重新打开并核对每个实际卷。缺卷映射使用当前 resolver；原位置文件恢复、替代卷变化或只修改 ChangeTime，都会使旧身份失效。resolver 明确失败直接返回，避免一次打开重复弹出换卷请求。

前置发现和引擎排队采用 **无进展超时**。真实目录项、新卷和身份复核的进展刷新计时；单纯重复尝试引擎锁不会刷新。持续工作的较大卷组不会被固定总时限误判。

同步 resolver 和阻塞系统 I/O 仍只能在返回后检测超时／取消，不能保证强制中断回调内部。固实解码字典共享、跨曲目自动预取不属于本次新增能力。归档保持只读。

密码能力的契约已经补入 SDK：传入密码并不表示目标成员一定加密；加密成员由 DLL 完整认证，未加密成员允许继续渐进读取。旧能力模块的兼容验证仍然保留。

### 2.4 验证期间确认的 CoolSB 线程竞态

本机一次压力检查返回初始化失败，原探针没有记录错误码，不能精确倒推该次原因。后续受控复现确认：线程在句柄收集后、暂停前退出，基线及中间构建都会因 `SuspendThread` 返回错误 5 而中止事务。

本次增加线程句柄的同步访问权。仅当 `DetourUpdateThread` 失败且该线程句柄已经变为终止状态，才完整 abort、释放所有句柄，再重新收集线程和建立事务；合计最多 3 次。不能继续已经失败的旧事务，也不能忽略仍然存活线程的错误。

安装和卸载各验证一次／两次线程退出后恢复、三次退出后停止，以及活线程权限错误不重试，共 8 项；另有无跟踪的正常 40 次循环通过。最终三系统主矩阵各完成 200 次安装／卸载，8 个原生调用线程均无滚动错误。

## 3. ReplayGain 与 CPU 基线

### 3.1 非有限 PCM

ReplayGain 在更新 peak、滤波器或直方图之前，检查整个输入批次的声道、容量和数值。包含 NaN 或正／负无穷时返回失败，实例保持提交前状态；调用方可以跳过错误数据，再继续提交有效数据。

这是明确的错误输入契约，不以原版错误输入下的未定义结果作为音频输出要求。有限输入的曲目／专辑增益和 peak 对照继续通过。

### 3.2 普通代码使用 IA32，SSE2 快路径必须检查能力

全局 `/arch:IA32` 在创建依赖目标前设置，覆盖核心和普通第三方 C／C++ 代码。不能因为 PE 子系统与导入支持 XP，就假定生成的指令也支持旧 CPU；现代 MSVC 的默认值为 SSE2，见 [Microsoft `/arch` 文档](https://learn.microsoft.com/en-us/cpp/build/reference/arch-x86?view=msvc-170)。

归档引擎已有的 AES／SHA 等指令优化继续保留运行时能力检查。音量软限幅增加一份独立的 SSE2 源文件，采用 `/arch:SSE2 /GL-` 和 `noinline`，只在 `IsProcessorFeaturePresent(PF_XMMI64_INSTRUCTIONS_AVAILABLE)` 成功后调用，防止跨文件优化把 SSE2 指令带入标量分支。

这样处理有实际数值依据：旧构建使用 `__libm_sse2_tan_precise`，标量构建使用 `_CItan`。仅改用普通 `tan` 或强制每步 double 舍入，并不能让两者所有结果相同。本次在现代 CPU 上保留原来的计算；无 SSE2 路径明确舍入中间值，并单独记录其数值边界。

实际最终 DLL 对照 1,516,362 组输入：支持 SSE2 时，double 及整数 8／16／24／32、浮点 32／64 PCM 输出均与修正前构建逐位一致。强制能力检查返回 false 时，SSE2 调用次数为零，标量结果与单独的标量构建一致。

标量与 SSE2 的浮点结果不承诺逐位相同，尤其是极小数和 tan 极点附近；所测整数及 float32 最终编码相同。测试机及虚拟机均具备 SSE2，本次没有实体无 SSE2 CPU 实测，也没有穷举所有非默认浮点控制字。

## 5. 交付与使用

输出位于用户指定目录 `rebuild/build/Release`：

- `ttpcomm.dll`：可用于原版宿主的替换验证，或配合当前重建播放器使用。
- `ttpcomm-2026.10.19.zip`：只包含 DLL 与 SHA256 清单。
- `TTPlayerRebuild-2026.10.19.zip`：通用播放器发行包，包含配套 DLL 和已验证的必需组件。

**重建播放器应更新完整包。** F3、F5、F7 含宿主改动，仅换 DLL 无法修正原 EXE 中的调用。原版播放器不会自动调用新增归档和标准标签扩展；不能把重建宿主的修正等同于原版 EXE 获得这些功能。

播放器组件使用本地未发布包验证，清单注明 `local-unpublished-build`，没有冒充 GitHub 已发布版本。现有 Actions 构建／ABI 检查保持运行，不运行本地测试。

远程构建仍按现有顺序：先发布对应 TTPlayerComm，再让播放器 Action 的 `latest` 取得该版本。本次本地打包已经配对，不表示远程 `latest` 已自动更新。
