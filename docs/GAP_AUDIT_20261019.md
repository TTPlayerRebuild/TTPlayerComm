# ttpcomm 原版与重建版差异复核（2026-10-19）

> 本文固定记录**修正前**的构建、复现和结论，以下“当前”均指审计时版本。后续已按本文建议修正，最新实现、最终哈希及验证范围见 [修正记录](GAP_FIXES_20261019.md)。

## 1. 结论与范围

当前重建版已实现原版 **67 个有效导出**，保留序号、名称、关键结构和 12／78 共用释放函数的关系；另有 500—503 四个扩展导出。原版接口没有发现新的缺失项。

剩余工作集中在 **7 项已确认问题**：2 项 DSP 异常恢复、3 项标准标签读取／保存接入、2 项归档缓存／密码接入。另外，ReplayGain 非有限输入处理和旧 CPU 最低要求需要明确契约。标签及归档中的部分问题位于重建播放器，单独更新 DLL 无法全部解决。

本次完成原版二进制／伪代码、当前源码和针对性探针对照，未修改生产实现，未提交 Git。私有测试留在 `rebuild/tests`，不进入发行包或 Actions。本文是当前差异审计；[重建实施记录](RECONSTRUCTION_STATUS.md) 保留此前实现和历史测试。

P1 表示优先处理的内存安全或有效输入读取错误；P2 表示随后处理的异常、保存语义或性能问题。

### 2.2 三类接口必须分开比较

| 层次 | 范围 | 对照要求 |
| --- | --- | --- |
| 原版 DLL 接口 | 1—401 中的 67 个有效导出，详见 [导出清单](../abi/exports.json) | 原版宿主／插件调用、布局、所有权和有效输入行为兼容 |
| 新增 DLL 接口 | 500 能力查询；501 标准标签／PCM／压缩运行接口；502／503 归档接口 | 按新接口契约验证；不能用“旧导出已通过”推导这些调用正确 |
| 播放器接入 | 标签与封面调用、文件写入、CUE、密码和缓存调度 | 需要检查宿主调用次序、标志和错误传播 |

原版 DLL 的 80—83 是 zlib 解压接口。ZIP／RAR 的目录、成员流和 CUE 调度主要在原版 EXE，例如 `004738B5`、`00473338`、`00474051`，ZIP 读取路径 `0041F185` 调用解压接口。

因此，新增归档服务属于从宿主抽取及扩展的能力；它们不应计为“原版 DLL 尚缺导出”。仅给原版 EXE 换入新 DLL，也不会自动使它调用新接口或支持 7z、RAR5 等新增格式。

## 3. DSP：必须修正的异常恢复

### F1：均衡器分配失败后重试越界

**原版依据：** 外层提交 `60007520`，每声道块处理 `60006FE0`；后者本轮重新用 REA／Ghidra 分析，见证据 E3。

**当前位置：** [equalizer.cpp](../src/equalizer.cpp)，104—109、130—141 行。

当前处理顺序：

1. 向 511 项的 `pending` 写入，`used` 增至 511。
2. 运行变换并推进 `overlap`。
3. `queue.insert` 为输出分配内存。
4. 最后才将 `used` 清零。

第 3 步抛出 `bad_alloc` 后，提交函数返回 false，但实例仍可继续使用。下次提交写入 `pending[511]`，超出数组边界；计数变为 512，又错过 `used == 511` 的处理条件。

直接编译当前实现，仅在首个 2,048 字节队列分配上注入一次失败：

```text
init=1 submit=0 used_after_failure=511 queue=0
retry=1 used_after_retry=512 overlap0=0.5
```

**建议：** 在推进滤波状态前完成所需分配，或让失败实例进入明确的不可继续状态，直至显式恢复。多声道必须一起规定失败前已经消费的数据如何处理，避免左右声道错位。不能只把 `used` 清零，因为 `overlap` 和部分声道已经改变。

**验收：** 首块／后续块、每个声道的失败注入；失败后的提交、读取、重置和重新初始化；无越界、无跨声道错位。该发现不表示原版的低内存路径安全。

### F2：SSRC 构造失败泄漏

**原版依据：** 包装初始化 `60005590`，上采样构造 `6000D230`，下采样构造 `6000E460`。

**当前位置：** [ssrc_support.h](../src/ssrc_support.h) 第 9 行、[resampler.cpp](../src/resampler.cpp) 20—29 行、[adapt_ssrc.py](../cmake/adapt_ssrc.py)。生成代码 `build/ssrc-adapted/ssrc.cpp` 308、314、320、321 行等连续分配裸指针。

适配分配器把失败改成异常；包装层捕获异常后返回 false，但对象构造未完成，派生类析构函数不会执行，前面已经成功分配的数组泄漏。

直接编译当前生成代码，使用行为等价的私有记录分配器，测试 44.1→48 kHz、双声道：

| 失败位置 | 返回后残留块 | 残留字节 |
| --- | ---: | ---: |
| 无失败 | 0 | 0 |
| 第 2 次分配 | 1 | 1,920 |
| 第 3 次分配 | 2 | 3,840 |
| 第 4 次分配 | 3 | 4,480 |
| 第 5 次分配 | 4 | 12,160 |

探针随后回收记录的内存，没有耗尽系统内存。动态证据覆盖上采样；下采样存在同类静态模式，本轮未穷举其分配点。

**建议：** 在适配脚本中加入 RAII 或构造失败清理，完整构造后再交给包装对象；不要只修改下次配置会被覆盖的生成文件。随后检查运行期输出缓冲分配失败是否发生部分消费。

## 4. ID3：旧导出与新标准接口之间的缺口

原版私有 ID3 实现和新版标准标签服务有不同职责。原版私有 v2.4 帧大小存在普通大端读取行为，标准 v2.4 使用 synchsafe 编码。旧导出应继续保留宿主依赖的行为，新标准服务应独立实现标准规则，不能简单把所有新路径改成调用旧 `@53`。

### F3：ID3v2.4 整块反同步破坏帧边界

“反同步”是去除标签为了避免误识别音频同步字而插入的字节。v2.4 必须保留存储的帧长度，逐帧处理；提前缩短整块数据会使后续帧起点错位。[ID3v2.4 结构规范](https://id3.org/id3v2.4.0-structure)

**原版依据：** `60022C0E` 仅在版本小于 4 时先整块反同步；v2.4 先划分帧，再由 `60021E02` 处理帧数据。前者本轮 REA 证据 E2。

**当前位置：**

- `rebuild/src/audio/builtin_file_info.cpp:590`：只检查标签头 `0x80`，未区分版本。
- `rebuild/src/ui/player_window_visual.cpp:209`：封面路径有同样处理。
- `builtin_file_info.cpp:626`：将头标志作为“已经反同步”的参数继续传入。

构造有效 v2.4 标签：标题和艺术家两帧均设置反同步位；标题原始数据为 `00 41 FF 00 E0 42`。

| 路径 | 结果 |
| --- | --- |
| 原版 DLL `@53` | 正确得到两帧 |
| 重建 DLL 旧 `@53` | 与原版相同 |
| 按当前宿主顺序调用实际运行接口 | 标题末尾混入下一帧标识中的 `T`，下一帧返回 `TTPCOMM_DATA (-4)` |
| 保留整块存储长度，逐帧调用 | 标题、艺术家正常，最终返回结束 |

**影响边界：** 当前宿主设置了 `rewrite_safe=false`，此样本证明的是读取错误和保存被禁止，不是已证明会破坏文件。封面具有相同调用缺陷；本轮动态样本是文本两帧，未进行真实封面 UI 对照。

**建议：** 同时修正标签和封面入口：v2.2／v2.3 按整块规则处理，v2.4 按帧处理；区分“原始头存在标志”和“数据已经变换”，不要继续共用一个布尔值。

### F4：标准扩展头校验弱于旧接口

**原版依据：** `60022C0E` 检查扩展头边界、字段和 CRC。

**当前位置：** [tags.h](../sdk/include/ttpcomm/tags.h) 28—36 行、[runtime_services.cpp](../src/runtime_services.cpp) 第 51 行。

当前 `FrameStart` 主要做长度跳过；v2.4 最小长度接受 4，而标准最小为 6，也未校验扩展字段和 CRC。[ID3v2.4 结构规范](https://id3.org/id3v2.4.0-structure)

实际 DLL 对照：

| 输入 | 原版旧接口 | 重建旧接口 | 重建标准接口 |
| --- | --- | --- | --- |
| v2.4 扩展头长度为 4 | 拒绝 | 拒绝 | 继续读取标题 |
| v2.3 扩展头 CRC 错误 | 拒绝 | 拒绝 | 继续读取标题 |

宿主目前依赖解析失败设置 `rewrite_safe=false`，这类输入可能进入可改写路径。本轮未通过 UI 保存这些样本，因此不宣称已观察到磁盘损坏。

**建议：** 补全版本对应的结构、标志字段和 CRC 验证；若允许容错读取，必须独立标明不可安全改写。同步更新 SDK 快照，保留旧导出行为。

### F5：保存未知帧时遗漏修改后丢弃标志

**原版依据：** 序列化 `6002221B` 检查标签修改／文件修改相关状态位。

**当前位置：**

- [tags.h](../sdk/include/ttpcomm/tags.h) 第 57 行和 [runtime_services.cpp](../src/runtime_services.cpp) 第 66 行：`flags` 只输出帧格式字节 `p[9]`；状态字节 `p[8]` 仍在 `raw` 中。
- `rebuild/src/audio/builtin_file_info.cpp:1334`：标签保存复制未知帧。
- 同文件 `1783` 附近：ReplayGain 写入也复制非目标原始帧，未判断这些状态位。

v2.4 未知帧 `XABC` 设置状态 `0x40`，再附带标题：

- 原版和重建旧接口均能读取两帧。
- 原版和重建旧序列化均只留下标题。
- 新运行接口报告 `flags=0`，但 `raw-status=0x40`；当前宿主保存代码会原样保留该未知帧。

这是实际旧接口对照加宿主源码路径证明，本轮未执行真实文件属性保存。

**建议：** 按版本处理 tag-alter／file-alter 状态语义，并覆盖普通标签、封面及增益写入。可从原始帧头读取状态，或增加兼容的独立接口。**不要直接把 ABI 1 的 `flags` 改为合并的 16 位值**：现有 `TagDecode` 明确拒绝大于 255 的值，旧调用端也按格式字节使用。

### 4.1 可选标准增强：分组标识与反同步的顺序

分组 ID 为 `0xFF` 且启用帧反同步时，当前 `tags_zlib.h` 先跳过分组字节，再去除插入字节。原版也有类似边界问题：同一样本旧接口得到空标题，标准接口多出一个零字节。

它适合在标准服务中修正为按完整帧数据反同步后再拆解前缀；不宜无条件改变旧私有接口。DLI 与实际长度不一致的另一探针被三条路径同时接受，未列为重建独有回归。

## 5. 归档扩展：缓存与密码接入

### F6：RAR 缓存命中前被全局解压锁阻塞

**原版宿主依据：** `004DFDED` 先复用已有同路径对象，需要创建时才进入 `004DFBF9`。原版较弱的路径身份检查不应直接移植。

**当前链路：**

1. [archive_stream.cpp](../src/archive_stream.cpp) 第 275 行先执行 `identity.Open`。
2. 第 31 行转入 [archive_group.cpp](../src/archive_group.cpp) 第 45 行的实际 RAR 分卷发现。
3. [archive.cpp](../src/archive.cpp) 进入枚举，等待全局 `engine_mutex`。
4. 返回后，流服务第 281 行才查找缓存。
5. 流超时在 `Stream::Wait` 内；前述获取引擎锁只检查取消，没有使用该超时。

针对性探针先准备完整缓存，再让另一枚举持锁约 200 ms，打开设置 40 ms 超时：

```text
timeout_ms=40 finished_before_unlock=0 elapsed_ms=203
open_hr=0x0 cached_task=1 returned_task=1
```

确实复用了同一个缓存任务，但仍等到锁释放。另一个启用取消的探针约 110 ms 返回 `0x800704c7`，所以不能描述为取消完全失效。

**建议：** 保存已发现的实际卷组，先用文件身份校验判断能否直接复用；过期或未知卷组再重新发现。把前置发现和引擎排队纳入明确的超时／取消范围。保留每卷文件 ID、大小、修改时间、ChangeTime 和密码身份，不能退回仅比较路径。

**验收：** 完整缓存命中与其它 RAR 操作并发；未命中、取消、超时、缺卷、换卷以及保留修改时间覆盖文件。固实 RAR 向后成员仍可能需要解压前置数据，此修正不承诺所有跳转立即完成。

### F7：会话密码让未加密大成员被完整解压后才返回

**当前位置：**

- `rebuild/src/audio/archive_password.cpp:207` 优先尝试同包的会话密码。
- `rebuild/src/audio/archive_member.cpp:153` 只要密码指针非空，就执行 `Seek(END)` 和尾部读取校验。

这种策略没有区分当前成员是否加密。验证过同包加密 CUE 后，再打开未加密大 WAV，也会完整解压。

实际当前 DLL 与宿主调用代码探针，混合 ZIP 含加密 CUE 和约 128 MiB 未加密 WAV：

| 条件 | 打开返回时耗时 | complete | 已产生字节 |
| --- | ---: | ---: | ---: |
| 尚无会话密码 | 0 ms（计时精度内） | 0 | 0 |
| 已验证加密 CUE，存在会话密码 | 157 ms | 1 | 134,217,804 |

时间取决于压缩率和硬件；核心证据是返回时从渐进读取变成了 100% 完成。不能把 0 ms 理解成零成本，也不能由此推算用户 RAR 的等待秒数。

**建议：** 根据实际成员是否加密决定验证路径，或在确认 DLL 的能力和契约后移除宿主重复验证。现有 DLL 流已对加密成员执行完整验证门控。保留 ZipCrypto CRC／AES 认证、EOF 和最终错误检查，不能因启动速度而让错误密码的明文提前进入解码器。

### 5.1 继续保留的边界

- 所有归档保持只读；用户明确不要写回，原版相应流的写入／调整长度／提交也不提供该能力。
- ZIP、RAR、7z 的密码、卷组身份、流取消和最终校验已有实现，不能概括为“尚未实现”。
- 当前有三个有界成员保留槽；固实包字典复用、相邻成员预取和跨进程缓存仍可研究，但需要新设计及性能证据。
- PKWARE 强加密／隐藏目录、部分 TAR sparse 或未注册 7z 方法等能力边界，应明确返回不支持；这些不是原版 DLL 的缺失导出。
- CUE 与外置歌词／封面关联仍有宿主职责，不能只审查 DLL 就宣称端到端完全一致。

## 6. 两项需要明确契约的差异

### 6.1 ReplayGain 的 NaN／Infinity

原版 `60004450` 通过 `60010C48` 将非有限转换后的负值夹到第 0 桶；当前 [replaygain.cpp](../src/replaygain.cpp) 46—66 行把非有限能量放到第 11999 桶，且滤波状态已经被污染。

实际 DLL A/B，44.1 kHz、单声道、4,410 帧：

| 输入 | 原版增益 | 重建增益 |
| --- | ---: | ---: |
| 正常 0.5 | 14.72 dB | 14.72 dB |
| 首样本 NaN，其余 0.25 | 64.82 dB | -55.17 dB |
| 首样本 Infinity，其余 0.25 | 64.82 dB | -55.17 dB |

双方 process 均返回成功。Infinity 样本的 peak 双方均为 Infinity。

**影响限定：** 重建播放器 `replay_gain_scanner.cpp:76` 已拒绝非有限 PCM，第 403 行也检查最终结果。未发现它因此发生正常扫描错误；风险主要在直接使用 DLL 的原版或其它宿主。

**建议：** 明确拒绝非有限输入且不污染先前统计，补充失败后的继续处理测试。恢复原版的异常大增益没有实际收益。

### 6.2 XP 系统兼容不等于无 SSE2 的 CPU 兼容

当前主目标没有统一指定 `/arch:IA32`；部分依赖有单独设置。实际 Release 均衡器中观察到无条件 SSE2，例如：

```text
1000D7D9  cvtdq2pd xmm0,xmm0
1000D7E1  addsd    xmm1,xmm0
```

原版所复核的均衡器 `60006000—60007900` 区间未见 XMM 指令，`60006EC9` 使用 x87 `fsqrt`。这是该区间的事实，不能推导原版全部 DLL／播放器完全不含更高指令集。

现代 MSVC x86 默认 SSE2；`/arch:IA32` 使用传统浮点指令。编译选项和舍入差异见 [Microsoft /arch (x86)](https://learn.microsoft.com/en-us/cpp/build/reference/arch-x86?view=msvc-170)。

**建议二选一：**

1. 明确发布最低 CPU 要求为 SSE2。
2. 若要覆盖无 SSE2 的老 CPU，为全部相关模块建立基线构建或运行时指令分派，再做数值和性能对照。

本轮未在无 SSE2 CPU 上执行；XP／Win7 虚拟机支持 SSE2，静态导入检查也不检查 CPU 指令。不能据现有结果宣称这一硬件范围已覆盖。
